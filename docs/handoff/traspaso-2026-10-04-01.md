## 4. Known defects and findings to act on (priority order)

1. **Implausible pH in the Waterbase store.** A country-wide Italy comparison of pH returned a mean of site means of
   11.16 for 2017-2024 (7.95 for 2010-2016), which is not physical. Some monthly values are implausible (wrong unit or
   outliers). Fix at build time: apply physical plausibility bounds per parameter (reuse `is_physically_possible` of
   `src/oah/indices/water_parameter_limits.py` or the same idea for the new groups), drop and count the rows with a
   provenance counter, rebuild the store (`scripts/build_waterbase_store.py`, about 4 minutes, needs the archive and
   7-Zip on the maintainer's machine), re-stage and redeploy. Check other parameters for the same problem (temperature,
   conductivity, oxygen) with a quick scan of min and max per determinand and country.
2. The model once wrote a site name with wrong letters ("STABILIVENTO" for "STABILIMENTO"). Grounding checks numbers and
   units, not names. Consider telling the model to copy site names exactly and adding a name check against the tool
   results.
3. The maintainer's local settings name an older, dearer model (claude-opus-5) for local runs; the deployed service uses
   claude-sonnet-5-5. Their choice.
4. Items still unverified: first run of the CI workflows; the deployed behaviour under CPU throttling; Cloud Run memory
   use against the 2 GiB limit (procedure in `docs/deployment.md`); human review of the machine-drafted translations;
   attribution wording of GloFAS and GBIF; the licence wording of the bathing-water dataset.

## 6. What an online session does NOT have

The stores (Waterbase, bathing, samples) live outside the repository in the maintainer's data folder and are built by
scripts from public archives; the cloud service already has them baked into its image. The Python virtual environment,
the Google Cloud login, the secrets and the helper scripts used for building and smoke-testing the image are on the
maintainer's machine, not in the repository. So an online session can do the web app (against `docs/openapi.json`,
mocking responses, or against the service once it is public), documentation, the video script and the submission text,
and can run the test suite only if it installs the project from the hash-pinned lockfile; backend work that needs the
real stores or cloud actions needs the maintainer's machine.

## 7. Rules that bind every session

- Never run `git commit`, push or merge, and never change git configuration: the maintainer does it. Never add
  `Co-Authored-By` or any attribution line to a commit message or pull request (the maintainer prohibited it).
- Hooks block destructive commands, cloud exposure commands and any command naming secret files; do not work around them.
  Never read or print the real settings file or any secret. Write multi-line scripts to files.
- All code, tests and documentation in English; chat with the maintainer in Spanish. No absolute paths, personal names or
  private cloud names in the repository (a portability test checks). `reference/` is read-only; the out-of-scope stack
  folder is not used.
- Real, external-modelled and synthetic data are always labelled; no health or safety verdicts; reference values are
  never presented as legal compliance. Never invent codes, thresholds, formulas or sources.
- Read `docs/handoff/LEDGER.md` at the start of a turn and append a complete entry at the end.
